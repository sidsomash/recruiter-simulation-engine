# Ranking Rules v1.0
### (Generalized, Candidate‑Agnostic, Simulation‑Output‑Driven)

This document defines the scoring and ranking logic used by the **ranking skill**.
It is referenced by `skills/ranking/SKILL.md` and consumed at runtime to ensure
consistent, deterministic ranking behavior.

The ranking skill does **not**:
- run simulations  
- read job descriptions  
- read the candidate résumé  
- read the candidate profile  
- apply simulation logic  

It only consumes **simulation outputs** generated by the simulation skill.

For simulation output structure, see:
- `../simulation/assets/templates/simulation_output_template.md`
- `../simulation/references/simulation_contract.md`

---

## 1. Purpose
The ranking skill evaluates **multiple simulation outputs** and produces a
rank‑ordered list of roles based on:

- Recruiter decision likelihood  
- Degree alignment  
- Skill alignment  
- Experience alignment  
- Preference alignment  
- Overall fit category  

These dimensions are extracted directly from simulation outputs.

---

## 2. Required Inputs
The ranking skill expects **one or more simulation outputs**, each containing:

- Recruiter Takeaway  
- Skill & Responsibility Mapping  
- Skill Gaps  
- Years‑of‑Experience Mapping  
- Degree Requirement Mapping  
- Preference Violations  
- Recruiter Decision  
- Final Fit Summary  

These sections must be present for ranking to function correctly.

**Machine-readable source of truth:** Each simulation output has a required `.json` sidecar file
(same base filename, see `simulation_contract.md` §11 and `simulation_output_sidecar_template.json`).
The `.json` sidecar is the **canonical machine-readable source** the ranking skill should read
values from directly (no parsing/regex required). The `.md` file remains the **canonical
human-readable source** for the sections listed above. `run_ranking.py` reads the `.json` sidecar
when present, and falls back to regex-parsing the `.md` file only for older simulation outputs
that predate the sidecar.

---

## 3. Ranking Dimensions

Each simulation is evaluated across the following dimensions:

### 3.1 Recruiter Screen Likelihood (Primary Weight)
Higher recruiter screen probability → higher ranking.

### 3.2 Interview Likelihood (Secondary Weight)
Used as a tie‑breaker when recruiter screen likelihood is similar.

### 3.3 Degree Alignment
Degree match categories are scored as:

- ✔ Direct match → +3  
- ✔ Equivalent match → +2  
- ~ Partial match → +1  
- ✘ No match → −2  
- ❌ Hard mismatch → −5  

### 3.4 Skill Alignment
Based on the simulation’s skill mapping:

- High skill alignment → +3  
- Moderate skill alignment → +2  
- Low skill alignment → +1  
- Major skill gaps → −2  

### 3.5 Experience Alignment
Based on years‑of‑experience mapping:

- Meets requirement → +2  
- Partially meets → +1  
- Does not meet → −2  

### 3.6 Preference Violations
Preference violations reduce ranking score:

- Minor violation → −1  
- Moderate violation → −2  
- Major violation → −3  
- Defense/clearance violation (if candidate avoids) → −4  

If no preferences file was provided:
→ No penalties applied.

### 3.7 Final Fit Summary (Category Weight)
Fit categories are scored as:

- Strong match → +3  
- Moderate match → +2  
- Weak match → +1  
- Mismatch → −2  
- Hard reject → −5  

---

## 4. Scoring Formula

Each simulation receives a **composite score**:

Composite Score =
  (Recruiter Screen Likelihood * 0.45)
+ (Interview Likelihood * 0.20)
+ (Degree Alignment Score * 0.15)
+ (Skill Alignment Score * 0.10)
+ (Experience Alignment Score * 0.05)
+ (Fit Summary Score * 0.05)
- (Preference Violation Penalties)

All components are normalized to a 0–100 scale before weighting.

---

## 5. Ranking Rules

### 5.1 Primary Sort Key
- **Composite Score** (descending)

### 5.2 Secondary Sort Keys (tie‑breakers)
If two roles have similar composite scores (±3 points):

1. Higher recruiter screen likelihood  
2. Higher interview likelihood  
3. Better degree match  
4. Fewer preference violations  
5. Higher skill alignment  
6. Higher experience alignment  

### 5.3 Hard Reject Handling
If a simulation’s final fit summary is **Hard reject**, it is:

- Always ranked at the bottom  
- Ordered among other hard rejects by recruiter screen likelihood  

### 5.4 Internship Handling
If the simulation output indicates **Internship Mode**:

- Internship roles are ranked **separately** from full‑time roles  
- Two lists are produced:
  - Full‑time ranking  
  - Internship ranking  

This prevents internships from outranking full‑time roles or vice versa.

---

## 6. Output Requirements

The ranking skill must output:

### 1. **Ranked List**
Ordered list of roles with composite scores.

### 2. **Score Breakdown Table**
For each role:
- Recruiter screen likelihood  
- Interview likelihood  
- Degree score  
- Skill score  
- Experience score  
- Fit summary score  
- Preference penalties  
- Composite score  

### 3. **Top Insights**
A short summary explaining:
- Why the top roles ranked highest  
- Why certain roles ranked low  
- Any notable degree or skill mismatches  

### 4. **Final Recommendation**
A concise takeaway:
- “Top 3 roles to prioritize”  
- “Roles to avoid”  
- “Roles worth applying if time permits”  

---

## 7. Notes
- Ranking is **deterministic**: same inputs → same ranking.  
- Ranking is **agnostic** to JD content; it only reads simulation outputs.  
- Ranking does **not** override simulation logic; it aggregates it.  
- Ranking is **candidate‑agnostic** except for preference penalties.
